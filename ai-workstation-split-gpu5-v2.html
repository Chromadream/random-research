Executive Summary

The original 5-GPU single-box design presents significant deployment friction: 5 dual-slot GPUs need 10 physical PCIe slots, yet the best available 4U chassis offers only 7, forcing riser gymnastics. Thermal density (~3.5 kW in one enclosure) demands exotic cooling and risks throttling. Power delivery borders on the limits of a single domestic circuit. Operationally, the GLM-5.2 and Qwen3.6 workloads have fundamentally different requirements — co-locating them couples their fates.

Key new finding: With corrected GPU specs and Qwen3.6 model sizes, the Qwen box does not need an RTX 6000 Pro. An RTX 5090 (32 GB) comfortably runs Qwen3.6-35B MoE for 4+ concurrent users at less than a quarter of the cost. This means the two-box split can actually save significant money versus the original single-box design while eliminating all deployment problems.

Two-box outcome:
  • Eliminates the PCIe slot crisis (4 GPUs = 8 slots, fits in standard chassis)
  • Cools both boxes with commodity air cooling, no exotic water loops
  • Keeps per-box power under 3 kW (fits standard circuits)
  • Isolates failure domains (Qwen stays up when GLM reboots, and vice versa)
  • Costs ~A$10,500 less than a corrected single-box, or roughly break-even with the original estimate — while solving all deployment problems

3. How Continuous Batching Works

Continuous batching (also called in-flight batching or dynamic batching) is the mechanism that lets a single model instance serve multiple concurrent users efficiently. It is the critical piece that makes the VRAM numbers in Section 2 work in practice.

Traditional Batching vs. Continuous Batching

Traditional batching: Wait until N requests arrive, batch them, run full inference on the batch, return all results. A request arriving 1 ms after the batch starts waits for the entire batch to complete. Latency spikes, GPU time is wasted waiting for batch windows to fill.

Continuous batching: The GPU runs a single model instance. Requests stream in continuously. On every single forward pass (one token-generation step), the server packs all currently active requests into a batch — regardless of when each request started. A new request joins the very next forward pass, not after some batch finishes.

Visual Timeline

Time → Request A: [tok1][tok2][tok3][tok4][tok5][tok6] ← long generation Request B: [tok1][tok2] ← short, joined mid-flight Request C: [tok1][tok2][tok3] GPU forward pass: ██ ██ ██ ██ ██ ██ Batch size: 1 1 2 2 3 2 ← grows/shrinks every step

Key Properties

PropertyWhat it means
Single model copyOne set of weights in VRAM (~15 GB for Qwen 27B). All requests share it. No per-user copies needed.
Per-request KV-cacheEach user gets their own KV-cache allocation, growing token by token. 4 users with 32K context = 4 separate allocations totalling ~6 GB at peak.
Zero waitingNew users join the next step immediately. Completed generations drop out without disrupting others.
Near-constant per-token latencyAdding users slightly increases each forward pass (bigger batch = more compute), but per-token generation time stays roughly constant regardless of concurrency.
No instance isolation neededYou don't spin up 4 separate Qwen processes. One process handles all 4 users.

Why This Matters for the Qwen Box

Without continuous batching, serving 4 concurrent users might mean 4 separate model instances — 4 × 19 GB = 76 GB VRAM just for weights, requiring a 96 GB GPU. With continuous batching, you need only ~19 GB for the model plus ~8 GB for all 4 users' KV-caches = ~27 GB total. The RTX 5090's 32 GB fits this comfortably.

Both vLLM and llama.cpp server (with --cont-batching) support this out of the box. You simply set --max-num-seqs 4 (or your peak concurrency) and the server handles the rest.

8. Software Architecture: Inter-Box Offload Pattern

8.1 The Offload Decision

The Qwen box runs the Offload Router — thin middleware between the user-facing chat API and the two inference backends:

User ──► [Chat API] ──► [Offload Router] ──┬──► Qwen3.6 (local RTX 5090)  ──► User
                                           │
                                           └──► GLM-5.2 (Box 1, 10.0.0.1:8080) ──► User

Offload triggers (configurable):

  1. Keyword/Intent classifier: Regex or distilled classifier detects complexity indicators ("analyze codebase", "architectural review", "write implementation", "debug complex").
  2. Qwen self-assessment: Prompt Qwen with: "Rate task complexity 1–10. If >=7, recommend large-model offload." Parse the response.
  3. Explicit user routing: /glm <message> forces GLM; /qwen <message> forces local.
  4. Fallback on low confidence: If Qwen output contains "I'm not sure", "I can't fully", or has unusually short output, retry on GLM.

8.2 API Contract

GLM Box exposes OpenAI-compatible endpoints:

POST http://10.0.0.1:8080/v1/chat/completions
GET  http://10.0.0.1:9090/health
GET  http://10.0.0.1:9090/metrics

Served via vLLM or llama.cpp server with tensor parallelism across all 4 GPUs. The OpenAI-compatible API means the Qwen box can use standard openai Python library pointed at http://10.0.0.1:8080/v1.

8.3 Concurrent Session Management (Qwen Box)

With RTX 5090 (32 GB) and Qwen3.6-35B MoE IQ4_XS (~19 GB model):

Deployment strategyVRAM usageMax users
Single instance, vLLM continuous batching~19 GB + ~4–8 GB KV-cache4–8 users efficiently interleaved
Two instances (27B + 35B MoE)~15 + ~19 = 34 GBFails — exceeds 32 GB
One 35B MoE instance, prefix caching~19 GB + variable cache4–6 users typical

Recommended: One Qwen3.6-35B MoE IQ4_XS instance with vLLM continuous batching. Serves 1–4 chat users and automation workloads from the same model efficiently. No need for separate instances.

8.4 Claw-Like Automation Engine

A lightweight framework (LangChain, CrewAI, or bespoke event loop) running on the Qwen box:

[Trigger: cron/webhook/filesystem] → [Qwen3.6: tool-calling]
    ├── Simple task → [Qwen executes tool] → [Result]
    └── Complex task → [Offload Router → GLM-5.2] → [Result]

Example flows:

  • PR watcher: New PR → Qwen triages → complex review offloaded to GLM → comment posted
  • Code generator: User prompt → Qwen drafts → offload to GLM for refinement → return
  • Monitoring agent: Alert fires → Qwen diagnoses → critical issue escalated to GLM

11. Deployment Sequence

  1. Procure both boxes in parallel. Consumer components from Australian retailers (PCCG, Mwave, Scorptec). RTX 6000 Pro GPUs may have 4–6 week B2B lead time; RTX 5090 available retail.
  2. Assemble GLM Box (4 GPUs, Threadripper, Define 7 XL). 4 GPUs plug directly into slots 1, 3, 5, 7. ~4 hours.
  3. Assemble Qwen Box (1 GPU, Ryzen, Meshify 2 Compact). Standard single-GPU build. ~1.5 hours.
  4. OS & drivers: Ubuntu 24.04 LTS both boxes. NVIDIA driver 550+, CUDA 12.6. Docker + NVIDIA Container Toolkit.
  5. Network: CAT6a direct 10GbE link. Static IPs (/30 subnet). Verify iperf3 ≥9.4 Gbps.
  6. Deploy GLM-5.2: vLLM or llama.cpp server across 4 GPUs (tensor parallelism = 4). OpenAI-compatible API on port 8080.
  7. Deploy Qwen3.6: vLLM on single RTX 5090 with continuous batching (--max-num-seqs 4). Verify multi-user concurrent requests.
  8. Deploy Offload Router: FastAPI + openai SDK. Route to local Qwen or remote GLM based on complexity heuristic.
  9. Firewall: UFW rules from Section 7.3. Verify inter-box connectivity and isolation.
  10. Load test: 4 concurrent Qwen users + 4 concurrent GLM offloads. Monitor GPU temps (target <80°C), power draw, p50/p99 latency.
  11. Handover: IP plan diagram, wiring diagram, API endpoints, health check URLs, SSH keys.

Qwen box downGLM box unaffected. Users lose chat until Qwen box recovers. Acceptable MTTR for a 1–4 user system.
RTX 5090 VRAM insufficient for future QwenIf Qwen4.x ships at 70B+, swap RTX 5090 for RTX 6000 Pro (~A$20,000) or add a second 5090 for tensor-parallel. The consumer platform (AM5, 1000W PSU) supports the upgrade path.
Power circuit overloadTwo-box splits across two circuits. Combined peak 3,660 W fits safely on a single 20 A circuit (4,600 W) with margin.
GPU failureBox 2 GPU failure: Qwen down, GLM continues. GLM Box GPU failure: Fall back to 3-GPU inference (slower, still functional). Keep a cold-spare RTX 5090 if high-availability is required.

13. Recommendations

  1. Split GPU 5 into a dedicated Qwen box. Solves the slot/cooling/power crisis with zero downsides.
  2. Use an RTX 5090 (32 GB) for the Qwen box, not an RTX 6000 Pro (96 GB). Qwen3.6-35B MoE at IQ4_XS needs only ~27 GB for 4 concurrent users with continuous batching. The 6000 Pro's extra 74 GB VRAM would sit idle at 600 W of wasted power and ~A$13,500 of wasted budget. The 5090 at A$6,500 (current Australian retail) is the right tool for the job.
  3. Use continuous batching (vLLM or llama.cpp server). One model instance serves all users by packing active requests into every forward pass. No per-user model copies needed. This is what makes the VRAM math work.
  4. Use Fractal Define 7 XL for the GLM box (9 PCIe slots, 4 GPUs plug directly, zero risers).
  5. 10GbE direct link between boxes (~A$249 NIC). Commodity cost, permanent network headroom.
  6. Deploy the Offload Router as a first-class service on the Qwen box. It's the architectural linchpin that makes the two-box system transparent to end users.
  7. If you must have matching GPUs or need to future-proof for much larger Qwen models, the RTX 6000 Pro option adds ~A$13,500. Only do this if there's a concrete plan to deploy a model that needs >32 GB in the Qwen box within 12 months.
